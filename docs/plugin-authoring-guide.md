# TestForge Plugin Authoring Guide

Each TestForge plugin integrates a specific Vue library into the unified component mounting pipeline.

A plugin is responsible for:

- describing its configuration through strict TypeScript types;
- creating the Vue plugin or runtime instance used during mounting;
- optionally providing a minimal project-independent default configuration;
- exposing a consistent package-level API for presets, applications, and tooling.

A plugin should understand the library it integrates, but it should not make application-specific configuration decisions on behalf of the consuming project.

## Architecture & File Structure

New plugins should follow this structure:

```text
packages/vue-test-plugin-custom/
└── src/
    ├── index.ts                    # Public package entry point
    ├── defaults.ts                 # Optional project-independent defaults
    ├── constants/
    │   └── constants.ts            # Plugin name and package-level constants
    ├── module/
    │   ├── customPlugin.ts         # PluginModule definition
    │   └── createCustomPlugin.ts   # Isolated runtime creation logic
    └── types/
        ├── types.ts                # Public options and optional runtime types
        └── augmentation.ts         # PluginOptionsMap / PluginInstanceMap
```

`defaults.ts` is optional. A plugin should expose defaults only when a safe project-independent baseline exists.

TestForge supports two integration categories:

| Category                                     | Helper                   | `create()` result                | Managed instances |
| -------------------------------------------- | ------------------------ | -------------------------------- | ----------------- |
| Factory-based (Pinia, Router, I18n, Vuetify) | `createPluginInstance()` | Vue-installable runtime instance | Yes               |
| Install-based (PrimeVue)                     | `createVuePlugin()`      | `[plugin, options]` tuple        | No                |

The **managed instance registry**, `PluginInstanceMap`, distinguishes these categories at the type level. Do not register an install-based plugin in that map.

## Step-by-Step Implementation

### Step 1: Define Plugin Types (`types/types.ts`)

For a factory-based plugin, define three distinct concepts: the **native/public options**, the **managed instance type**, and the **internal runtime options**.

```typescript
import type { CustomInstance, CustomOptions } from "some-vue-library";
import type { RuntimePluginOptions } from "@testforgejs/vue-test-core";
/** Configuration supplied by consumers and presets. */
export type VueTestCustomOptions = CustomOptions;
/** Options received by the TestForge-managed instance factory. */
export type CustomRuntimeOptions = RuntimePluginOptions<CustomInstance, VueTestCustomOptions>;
```

Use the upstream instance type when possible. For libraries exporting only a factory, use its return type:

```typescript
import type { createVuetify } from "vuetify";
export type VuetifyInstance = ReturnType<typeof createVuetify>;
```

If TestForge needs its own configuration fields, add them to `VueTestCustomOptions`. Before calling the native factory, remove any TestForge-specific fields that the library does not understand (as the Pinia integration does with its `MOCK_STORES` symbol).

**Do not extend public options with `PluginControlOptions<TInstance>`.** Managed instance controls are added automatically by core configuration types when the plugin is registered in `PluginInstanceMap`. `PluginControlOptions` is no longer part of the public plugin-authoring contract.

`RuntimePluginOptions<TInstance, TOptions>` adds internal capture and shared-instance controls used by `createPluginInstance()`. The input metadata generated by `withPluginInstance()` is resolved by the Mount Pipeline **before** the runtime factory receives its options; it is not a field of `RuntimePluginOptions`.

For an install-based plugin, use the library's configuration type directly. It has **no** managed instance runtime options:

```typescript
import type { PrimeVueConfiguration } from "primevue/config";
export type VueTestPrimeVueOptions = PrimeVueConfiguration;
```

### What is the managed instance type?

For factory-based plugins, it is the Vue-installable runtime value created by the upstream factory (or reused from a consumer-provided instance), subsequently passed to Vue Test Utils through `global.plugins`.

Examples:

- Pinia → `TestingPinia` for the testing integration;
- Vue Router → `Router`;
- Vue I18n → `I18n`;
- Vuetify → `ReturnType<typeof createVuetify>`.

An install-based integration returns a mount tuple, not a separately managed instance. Merely having a Vue plugin object with an `install()` method does not make it a TestForge-managed instance.

---

### Step 2: Define the Plugin Name (`constants/constants.ts`)

Define the plugin identifier once and reuse it throughout the package:

```typescript
export const CUSTOM_PLUGIN_NAME = "custom" as const;
```

The plugin name must match:

- the key registered in `PluginOptionsMap`;
- the key registered in `PluginInstanceMap` **if** the plugin supports managed instances;
- the value returned by `getName()`;
- the standardized package export `PLUGIN_NAME`.

Keeping the identifier in one constant prevents the runtime and type-level names from drifting apart.

---

### Step 3: Register Plugin Types (`types/augmentation.ts`)

Every integration extends `PluginOptionsMap` so TestForge and the consumer's IDE recognize the plugin key and its public configuration.

**Factory-based plugins must additionally extend `PluginInstanceMap`:**

```typescript
import { CUSTOM_PLUGIN_NAME } from "../constants/constants.js";
import type {} from "@testforgejs/vue-test-core";
import type { CustomInstance } from "some-vue-library";
import type { VueTestCustomOptions } from "./types.js";

declare module "@testforgejs/vue-test-core" {
  interface PluginOptionsMap {
    [CUSTOM_PLUGIN_NAME]: VueTestCustomOptions;
  }
  interface PluginInstanceMap {
    [CUSTOM_PLUGIN_NAME]: CustomInstance;
  }
}
```

The two registries have different responsibilities:

| Registry            | Responsibility                                                                                                                 |
| ------------------- | ------------------------------------------------------------------------------------------------------------------------------ |
| `PluginOptionsMap`  | Registers the plugin name and the public configuration type.                                                                   |
| `PluginInstanceMap` | Registers the managed instance type and enables typed `captureInstance()`, `withPluginInstance()`, and `fromPluginInstance()`. |

`PluginInstanceMap` is an **opt-in capability contract**: an absent key means the three instance-management mechanisms are unavailable for that plugin. If instance management is supported but no more specific instance type is known, a plugin may explicitly register its key with type `unknown`; do not rely on an implicit `unknown` fallback.

**Install-based plugins register only `PluginOptionsMap`:**

```typescript
import { PRIMEVUE_PLUGIN_NAME } from "../constants/constants.js";
import type {} from "@testforgejs/vue-test-core";
import type { VueTestPrimeVueOptions } from "./types.js";

declare module "@testforgejs/vue-test-core" {
  interface PluginOptionsMap {
    [PRIMEVUE_PLUGIN_NAME]: VueTestPrimeVueOptions;
  }
}
```

Registration is type-level: the module's runtime definition must also match its capabilities. For managed plugins that support deferred references, set `supportsInstanceReferences: true` in `getDefinition()` (Step 6).

---

### Step 4: Define Plugin Defaults (`defaults.ts`)

A plugin may expose a project-independent baseline through `getDefaultOptions()`.

Default options are optional.

Use `PluginDefaultOptionsFactory<TOptions>`:

```typescript
import type { PluginDefaultOptionsFactory } from "@testforgejs/vue-test-core";
import type { VueTestCustomOptions } from "./types/types.js";
export const defaultOptions: PluginDefaultOptionsFactory<VueTestCustomOptions> = () => () => ({
  // Only configuration required for a safe,
  // project-independent integration baseline.
});
```

The outer function may use TestForge runtime context such as a supplied test runner. The inner options factory creates a fresh options object for each pipeline execution.

For example, a runner-aware plugin may use:

```typescript
export const defaultOptions: PluginDefaultOptionsFactory<VueTestCustomOptions> =
  (runner) => () => ({
    createSpy: runner?.fn,
  });
```

#### Defaults are opt-in

Providing `getDefaultOptions()` does **not** cause TestForge to apply those options automatically.

This:

```typescript
manifest: [
  {
    module: customPlugin,
    enabled: true,
  },
],
```

only declares that the plugin is available and enabled.

It does not imply:

```typescript
customPlugin.getDefaultOptions();
```

A preset must explicitly choose to use plugin defaults:

```typescript
defaults: {
  custom: customPlugin.getDefaultOptions(),
},
```

Therefore:

```text
manifest inclusion ≠ default configuration
```

This distinction is intentional.

A plugin may gain or change `getDefaultOptions()` without silently changing presets that do not reference those defaults.

## Designing Good Plugin Defaults

Plugin defaults represent the library-level baseline known by the plugin.

They should not represent the consuming application's configuration policy.

A good default configuration follows these principles.

### 1. Functional, not merely constructable

Defaults should provide a useful integration for ordinary component tests when such a baseline exists.

A configuration that only prevents the library constructor from throwing is not necessarily sufficient if the resulting plugin cannot perform its normal testing role.

At the same time, functionality should not be achieved by inventing application behavior.

### 2. Project-independent

Defaults must not require knowledge of the consuming application.

Avoid embedding application-specific values such as:

- application routes;
- translation messages;
- application locale;
- store state;
- themes or design-system policy;
- API endpoints;
- application-specific plugins;
- business configuration.

Those belong in a project preset.

### 3. Minimal

Add only configuration that is necessary for a reliable TestForge integration.

Do not repeat upstream defaults merely to make the options object more explicit.

For example, if the upstream library already defaults an optional field to an empty object and TestForge does not need to override that behavior, omit the field.

### 4. Preserve upstream behavior unless TestForge has a reason to override it

The integrated library should remain the owner of its own defaults.

TestForge should override upstream behavior only when doing so is necessary to provide a reliable, consistent, or appropriately isolated integration.

This reduces unnecessary TestForge policy and lowers the risk of divergence from future library behavior.

### 5. Avoid application policy

A plugin understands the library.

A preset understands the application.

Conceptually:

```text
Plugin
→ library knowledge
→ safe project-independent baseline
Preset
→ application/test-environment knowledge
→ routes, locales, themes, state, messages, etc.
```

For example, a Router plugin may choose an isolated history implementation because that concerns test integration, but it should not invent application routes.

### 6. Prefer deterministic and isolated test behavior

When TestForge must choose between multiple valid upstream configurations, prefer the option that avoids unnecessary dependency on ambient state.

Examples include:

- avoiding browser URL state when an isolated memory implementation is sufficient;
- avoiding shared mutable configuration;
- creating fresh runtime values for each options-factory invocation.

Environment-dependent behavior should be introduced only when it is required or explicitly requested.

### 7. Keep behavior consistent across the supported version range

Plugin defaults must work across the versions declared by the package's peer dependencies.

If an upstream default changed between supported major or minor versions, the plugin may explicitly configure the option when a stable TestForge baseline is important.

Do not assume that a default observed in the latest upstream version existed across the entire supported range.

### 8. Do not suppress useful diagnostics without a specific integration reason

Warnings and validation messages belong to the integrated library unless TestForge has a strong reason to alter them.

A quieter test output is not by itself sufficient reason to hide useful upstream diagnostics.

Projects that intentionally want different warning behavior can configure it in their presets.

### 9. Return fresh configuration

`getDefaultOptions()` returns an options factory.

Each invocation should produce fresh mutable configuration where necessary:

```typescript
const factory = customPlugin.getDefaultOptions();
const first = factory();
const second = factory();
first !== second;
```

Do not share mutable option objects or runtime instances through plugin defaults.

### 10. Omit defaults when no safe baseline exists

`getDefaultOptions()` is optional for a reason.

If the library cannot be meaningfully configured without application-specific information, do not invent that information.

Use `PluginModule` without `getDefaultOptions()` and require the preset to provide configuration explicitly.

## Plugin Defaults vs Preset Defaults

Plugin defaults are a reusable source of configuration.

A preset explicitly decides whether to use them.

For example:

```typescript
const preset = {
  manifest: [
    {
      module: customPlugin,
      enabled: true,
    },
  ],
  defaults: {
    custom: customPlugin.getDefaultOptions(),
  },
};
```

A project preset can instead define its own configuration:

```typescript
const preset = {
  manifest: [
    {
      module: customPlugin,
      enabled: true,
    },
  ],
  defaults: {
    custom: () => ({
      projectSpecificOption: true,
    }),
  },
};
```

The important distinction is ownership:

```text
Plugin defaults
→ reusable library integration baseline
Preset defaults
→ explicit configuration selected by the preset
Project configuration
→ application-specific policy
```

TestForge does not automatically fall back to `getDefaultOptions()` when a preset omits configuration.

### Step 5: Implement the Isolated Factory (`module/createCustomPlugin.ts`)

Choose the helper based on **how the upstream Vue library is integrated**, not merely on whether the TestForge plugin has a `create()` hook. Every TestForge plugin has `create()`; its return value may be either an instance or an install tuple.

| Upstream integration                                                | TestForge helper         | Result                                 | Instance controls |
| ------------------------------------------------------------------- | ------------------------ | -------------------------------------- | ----------------- |
| A factory creates a Vue-installable instance                        | `createPluginInstance()` | Managed instance                       | Supported         |
| An existing Vue plugin is installed with `app.use(plugin, options)` | `createVuePlugin()`      | `[plugin, options]` for Vue Test Utils | Not supported     |

**Factory-based integration:** accept `CustomRuntimeOptions`, but specify only **native options** as the second generic argument to `createPluginInstance()`:

```typescript
import { createPluginInstance } from "@testforgejs/vue-test-core";
import { createCustomLibraryInstance } from "some-vue-library";
import type { CustomInstance, CustomOptions } from "some-vue-library";
import type { CustomRuntimeOptions } from "../types/types.js";

/** Creates or reuses the managed plugin instance. */
export function createCustomPlugin(options: CustomRuntimeOptions): CustomInstance {
  return createPluginInstance<CustomInstance, CustomOptions>(createCustomLibraryInstance, options);
}
```

`createPluginInstance()`:

1. Reads the internal capture callback and any supplied shared instance.
2. Builds a **new native options object** without the internal TestForge keys, leaving the original options unchanged.
3. Reuses the supplied instance when present; otherwise invokes the native factory.
4. Passes the resulting instance to the `captureInstance()` callback, including for reused instances.

TestForge-specific fields unrelated to those shared instance controls remain the integration's responsibility: strip or process them before invoking `createPluginInstance()`. A native option literally named `expose` is **not** a TestForge capture callback and is not stripped by this helper.

**Install-based integration:** use `createVuePlugin()` instead. It returns the tuple used by Vue Test Utils, without constructing or capturing a separate instance. See [Install-based Plugins](#2-install-based-plugins).

Do not reimplement capture, shared-instance reuse, or internal-option filtering inside individual managed plugins.

---

### Step 6: Define the Plugin Module (`module/customPlugin.ts`)

A factory-based plugin **without defaults** can use `PluginModule`:

```typescript
import { CUSTOM_PLUGIN_NAME } from "../constants/constants.js";
import { createCustomPlugin } from "./createCustomPlugin.js";
import type { PluginModule } from "@testforgejs/vue-test-core";
import type { CustomInstance, CustomOptions } from "some-vue-library";

export const customPlugin: PluginModule<CustomInstance, CustomOptions> = {
  getName: () => CUSTOM_PLUGIN_NAME,
  getDefinition: () => ({
    create: createCustomPlugin,
    supportsInstanceReferences: true,
  }),
};
```

For a plugin that provides defaults, use `PluginModuleWithDefaults`:

```typescript
import { CUSTOM_PLUGIN_NAME } from "../constants/constants.js";
import { defaultOptions } from "../defaults.js";
import { createCustomPlugin } from "./createCustomPlugin.js";
import type { PluginModuleWithDefaults } from "@testforgejs/vue-test-core";
import type { CustomInstance, CustomOptions } from "some-vue-library";

export const customPlugin: PluginModuleWithDefaults<CustomInstance, CustomOptions> = {
  getName: () => CUSTOM_PLUGIN_NAME,
  getDefinition: () => ({
    create: createCustomPlugin,
    supportsInstanceReferences: true,
  }),
  getDefaultOptions: defaultOptions,
};
```

For custom public options distinct from `CustomOptions`, use `VueTestCustomOptions` as the second `PluginModule` generic. This is the **public configuration type**; the dedicated adapter function accepts `CustomRuntimeOptions`.

`PluginDefinition` contains an optional runtime capability flag:

```typescript
supportsInstanceReferences?: true;
```

Set it to `true` for managed plugins supporting deferred instance dependencies through `fromPluginInstance()`. It is **not** a replacement for augmentation: `PluginInstanceMap` provides static support and the runtime definition must agree with it. Install-based plugins should not set this flag or register an instance type.

`getDefaultOptions()` remains optional. Use `PluginModuleWithDefaults` when the package contract guarantees that defaults are available.

### Step 7: Export the Package API (`index.ts`)

Import the augmentation module so it is included in the package declaration graph. Keep the descriptive exports for consumers and expose three **standardized package exports** for presets and tooling:

```typescript
import "./types/augmentation.js";

export { customPlugin, customPlugin as plugin } from "./module/customPlugin.js";
export { CUSTOM_PLUGIN_NAME as PLUGIN_NAME } from "./constants/constants.js";

export * from "./types/types.js";
export type { VueTestCustomOptions as PluginOptions } from "./types/types.js";
```

The standardized package contract is:

| Export          | Kind          | Purpose                                                               |
| --------------- | ------------- | --------------------------------------------------------------------- |
| `plugin`        | Runtime value | The `PluginModule` used in preset manifests.                          |
| `PLUGIN_NAME`   | Runtime value | The plugin identifier used as a configuration key.                    |
| `PluginOptions` | Type-only     | The public configuration type used by presets and TypeScript tooling. |

`PluginOptions` is an **alias of the existing public options type**, not a new options interface. Preserve descriptive exports such as `VueTestCustomOptions` for direct consumers. Both factory-based and install-based plugins expose `PluginOptions`; the alias must refer to their **public** options, never to `RuntimePluginOptions` or internal instance controls.

#### Using standardized exports in preset generation

A CLI generator can use the same import names for every plugin package and assign descriptive local aliases when generating an editable TypeScript preset. For example, for Vue Router:

```typescript
import {
  plugin as routerPlugin,
  PLUGIN_NAME as ROUTER_PLUGIN_NAME,
} from "@testforgejs/vue-test-plugin-router";
import type { PluginOptions as RouterPluginOptions } from "@testforgejs/vue-test-plugin-router";
import { createMemoryHistory } from "vue-router";

const routerDefaults = () =>
  ({
    history: createMemoryHistory(),
    routes: [],
  }) satisfies RouterPluginOptions;

export const preset = {
  manifest: [{ module: routerPlugin, enabled: true }],
  defaults: {
    [ROUTER_PLUGIN_NAME]: routerDefaults,
  },
};
```

The generated code remains editable and type-checked against the plugin's native/public options. This does **not** require the CLI to know the package-specific name `VueTestRouterOptions`.

`PluginOptions` is erased when TypeScript is compiled. It is suitable for **generating and checking TypeScript source**, but it is **not** runtime metadata: importing a plugin package cannot reveal its option keys, build an interactive configuration form, or validate an options object at runtime. Those tasks would require a separate runtime schema or metadata contract.

## Plugin Lifecycle

A TestForge plugin may participate in three lifecycle stages:

```text
Resolved plugin options
    ↓
beforeCreate(ctx, options)
    ↓
create(options)
    ↓
afterCreate(plugin, ctx)
```

Plugin defaults are resolved by the preset/pipeline before this lifecycle.

`beforeCreate()` should therefore not be used to implicitly apply `getDefaultOptions()`.

### `beforeCreate(ctx, options)`

Executed before the plugin is created or its install tuple is prepared.

Typical use cases:

- normalize resolved runtime configuration;
- derive runtime values from pipeline state;
- adapt options based on other enabled plugins;
- perform plugin-specific preprocessing that cannot be expressed statically.

It must return the final options passed to `create()`; managed instance controls remain subject to the normal pipeline rules.

```typescript
beforeCreate(ctx, options) {
  return {
    ...options,
    normalizedOption: true,
  };
}
```

Avoid using `beforeCreate()` to introduce hidden defaults that belong in `getDefaultOptions()` or in a preset.

### `create(options)`

Returns a mountable value. For factory-based plugins this is the managed runtime instance; for install-based plugins it is the `[plugin, options]` tuple.

This hook is mandatory:

```typescript
create: createCustomPlugin;
```

### `afterCreate(plugin, ctx)`

Executed after the plugin's `create()` hook returns its mountable value.

Typical use cases:

- activating an instance in an upstream library;
- registering runtime helpers;
- synchronizing plugin state with external library state.

Example:

```typescript
afterCreate(instance) {
  setActivePinia(instance);
}
```

Most plugins need only `create()`.

## Plugin Categories

TestForge supports two main categories of Vue integrations. The category determines the value returned by `create()`, the core helper, and whether instance management is available. Having a TestForge `create()` hook does **not** imply that a third-party instance was created.

### 1. Stateful Factory Plugins

These libraries expose a factory that creates a Vue-installable runtime instance: Pinia, Vue Router, Vue I18n, and Vuetify.

Typical upstream APIs:

```typescript
createTestingPinia();
createRouter({ history: createMemoryHistory(), routes: [] });
createI18n();
createVuetify();
```

The plugin adapter uses `createPluginInstance()` and a dedicated runtime type. For example, Router:

```typescript
import { createPluginInstance } from "@testforgejs/vue-test-core";
import { createRouter } from "vue-router";
import type { Router, RouterOptions } from "vue-router";
import type { RouterRuntimeOptions } from "../types/types.js";

export function createRouterPlugin(options: RouterRuntimeOptions): Router {
  return createPluginInstance<Router, RouterOptions>(createRouter, options);
}
```

Similarly, Vuetify:

```typescript
import { createVuetify } from "vuetify";
import { createPluginInstance } from "@testforgejs/vue-test-core";
import type { VuetifyOptions } from "vuetify";
import type { VuetifyInstance, VuetifyRuntimeOptions } from "../types/types.js";

export function createVuetifyPlugin(options: VuetifyRuntimeOptions): VuetifyInstance {
  return createPluginInstance<VuetifyInstance, VuetifyOptions>(createVuetify, options);
}
```

Characteristics:

- register both `PluginOptionsMap` and `PluginInstanceMap`;
- accept `RuntimePluginOptions` in the adapter;
- use `createPluginInstance()` to create or reuse an instance;
- support `captureInstance()`, `withPluginInstance()`, and `fromPluginInstance()`;
- set `supportsInstanceReferences: true` for deferred references;
- let core filter internal instance controls before calling the native factory.

The **plugin author** uses `createPluginInstance()`; the **test author** uses public instance helpers. Plugin authors should not implement a separate string-keyed `expose` callback.

#### Capturing an instance

```typescript
import { captureInstance } from "@testforgejs/vue-test-core";
import type { VuetifyInstance } from "@testforgejs/vue-test-plugin-vuetify";

const vuetifyCapture = captureInstance<VuetifyInstance>();

factory(
  {},
  {
    plugins: {
      vuetify: { ...vuetifyCapture },
    },
  },
);

// VuetifyInstance | undefined
const vuetify = vuetifyCapture.instance;
```

The `instance` getter is not copied into plugin options by object spread. Without an explicit generic, `captureInstance()` defaults to `unknown`; it does **not** infer the instance type from the `plugins` key.

#### Reusing an existing instance

```typescript
import { withPluginInstance } from "@testforgejs/vue-test-core";
import { createRouter, createMemoryHistory } from "vue-router";

const existingRouter = createRouter({
  history: createMemoryHistory(),
  routes: [],
});

factory(
  {},
  {
    plugins: {
      router: { ...withPluginInstance(existingRouter) },
    },
  },
);
```

When a pre-created instance is supplied, required native _creation_ options (such as `history` and `routes`) may be omitted from `mountOptions.plugins.router`. The native factory is not called for that instance. Extra native options supplied alongside the reused instance are not automatically reapplied to it.

#### Resolving dependencies from other managed plugins

`fromPluginInstance(pluginName, resolver)` represents a deferred value to be resolved from another managed plugin instance. Plugin names are restricted to `PluginInstanceMap`, and the callback receives the registered instance type.

```typescript
import { fromPluginInstance } from "@testforgejs/vue-test-core";
const currentPath = fromPluginInstance("router", (router) => router.currentRoute.value.fullPath);
```

The deferred reference can be used where the receiving plugin's configuration permits a value of the corresponding result type. The referenced plugin must be present and created in the applicable mounting pipeline; the runtime also requires its definition to support instance references.

`captureInstance()` and `withPluginInstance()` are supported in per-call `mountOptions.plugins` and `extraOptions.plugins`. **Do not put `captureInstance()` into factory-level `defaultMountOptions`**; that usage is prohibited at runtime.

### 2. Install-based Plugins

Install-based integrations expose an installable Vue plugin rather than a factory-created managed instance. PrimeVue is an example:

```typescript
import PrimeVue from "primevue/config";
import { createVuePlugin } from "@testforgejs/vue-test-core";
import type { PrimeVueConfiguration } from "primevue/config";
export type PrimeVueMountPlugin = [typeof PrimeVue, PrimeVueConfiguration];
export type VueTestPrimeVueOptions = PrimeVueConfiguration;

export function createPrimeVuePlugin(options: VueTestPrimeVueOptions): PrimeVueMountPlugin {
  return createVuePlugin(PrimeVue, options);
}
```

`createVuePlugin()` returns `[plugin, options]` without calling `install()` itself. Vue Test Utils installs the plugin during mounting. It does not create or reuse a managed instance; the helper rejects internal TestForge instance controls if passed at runtime.

Characteristics:

- register **only** `PluginOptionsMap`, not `PluginInstanceMap`;
- use `createVuePlugin()` to produce the mount tuple;
- do **not** support `captureInstance()`, `withPluginInstance()`, or `fromPluginInstance()`;
- let Vue Test Utils / Vue perform installation normally.

Both categories may expose `getDefaultOptions()` when a safe project-independent configuration exists.

---

## Which Plugin Category Should I Choose?

Use a factory-based plugin when the upstream library's normal integration creates a dedicated Vue-installable instance (e.g., `createRouter()`, `createI18n()`, `createVuetify()`). Use an install-based plugin when the normal integration installs a plugin object or function via `app.use(SomePlugin, options)`.

If the library supports both styles, prefer its factory API when that is the intended integration: it generally provides better instance isolation and enables TestForge instance-level features.

The current `scripts/scaffold-plugin.js` generates **factory-based plugins with managed instances only**. For an install-based plugin, adapt the files manually: omit `PluginInstanceMap` and `RuntimePluginOptions`, use the native options type, and call `createVuePlugin()`.

---

## Shared Instances

Factory-based plugins may reuse instances through `withPluginInstance()`. Plugin authors normally do not need to implement this themselves.

Using `createPluginInstance()` ensures that:

- an existing instance is reused rather than invoking the native factory;
- `captureInstance()` receives the newly created **or** reused instance;
- internal capture and shared-instance options are removed before the native factory call;
- the original options are not mutated and lifecycle processing continues.

Install-based plugins cannot reuse or capture TestForge-managed instances. Avoid duplicating plugin-specific side effects when a managed instance is reused.

## When Should I Use `beforeCreate()` and `afterCreate()`?

| Hook                  | Typical usage                                |
| --------------------- | -------------------------------------------- |
| `getDefaultOptions()` | Optional project-independent plugin baseline |
| `beforeCreate()`      | Runtime normalization or derivation          |
| `create()`            | Return a managed instance or install tuple   |
| `afterCreate()`       | Activate or synchronize the created instance |

Examples:

```text
Pinia
getDefaultOptions() → runner spy integration
create()            → createTestingPinia()
afterCreate()       → setActivePinia()
Router
getDefaultOptions() → isolated history + empty route table
create()            → createRouter()
I18n
getDefaultOptions() → Composition API integration baseline
create()            → createI18n()
Vuetify
getDefaultOptions() → library-level functional baseline
create()            → createVuetify()
```

Do not use lifecycle hooks merely to hide configuration that should be explicit in a preset or `getDefaultOptions()`.

## Testing Plugin Defaults

Defaults should be tested in the plugin package itself.

At minimum, verify the exact options returned:

```typescript
it("should provide default options", () => {
  expect(customPlugin.getDefaultOptions()()).toEqual({
    // expected plugin baseline
  });
});
```

Also verify that those options can create a functional library instance:

```typescript
it("should create a functional instance using default options", () => {
  const options = customPlugin.getDefaultOptions()();
  const definition = customPlugin.getDefinition();
  const instance = definition.create(options);
  expect(instance).toBeDefined();
});
```

Keep the boundary between unit and integration tests clear:

```text
plugin package
→ exact defaults
→ factory behavior
→ library instance creation
integration package
→ TestForge pipeline
→ Vue Test Utils mounting
→ interaction with real components
```

For example, testing that an I18n default contains `globalInjection: true` belongs in the plugin package.

Testing that a mounted component actually receives `$t` through the complete TestForge mounting pipeline belongs in integration tests.

---

## Testing Instance Capabilities

Test public plugin typings with `tsd` in the integration package, in addition to testing native options and runtime behavior.

For a factory-based plugin registered in `PluginInstanceMap`, check both `mountOptions.plugins` and `extraOptions.plugins`:

- `captureInstance<Instance>()` and `withPluginInstance(existingInstance)` are accepted;
- captures and supplied instances of incompatible types are rejected;
- required native creation options are enforced when no instance is supplied;
- passing a pre-created instance permits omitting required native creation options.

For an install-based plugin without `PluginInstanceMap` registration, check that native options are accepted but spreading `captureInstance()` or `withPluginInstance()` into its managed configuration is rejected in **both** option locations.

Run `tsd` against the package's built declarations (`dist`) to verify the consumer-facing module augmentation. Runtime integration tests should separately confirm instance creation, reuse, capture, dependency resolution, and errors for unsupported controls.

## Plugin Checklist

Before publishing a plugin, verify:

1. **Name alignment:** `getName()`, `PluginOptionsMap`, the plugin name constant, and `PLUGIN_NAME` all use the same identifier; `PluginInstanceMap` uses it too for managed plugins.
2. **Correct type registration:** Every plugin registers `PluginOptionsMap`. Only factory-based plugins supporting managed instance features register `PluginInstanceMap` with the actual instance type.
3. **Public/runtime separation:** Public options exclude TestForge instance controls. Managed factories accept `RuntimePluginOptions<Instance, PublicOptions>`; install-based plugins do not use that runtime type.
4. **Type augmentation is loaded:** `index.ts` imports `./types/augmentation.js`.
5. **Creation is isolated:** Runtime creation lives in a dedicated `create*.ts` adapter.
6. **Correct category and helper:** Managed instances use `createPluginInstance()`; install tuples use `createVuePlugin()`. Do not register install-based plugins as managed instances.
7. **Dependency support is aligned:** Managed plugins using `fromPluginInstance()` register their instance type and declare `supportsInstanceReferences: true` at runtime.
8. **Instance behavior is tested:** Capture, reuse, and incompatible types are checked in both `mountOptions.plugins` and `extraOptions.plugins`; unsupported controls are rejected for install-based plugins.
9. **Defaults are optional and opt-in:** Add `getDefaultOptions()` only when a safe project-independent baseline exists; manifest inclusion does not implicitly apply defaults.
10. **Defaults are minimal:** Do not repeat upstream defaults without an integration-specific reason.
11. **Defaults avoid application policy:** Do not embed project-specific routes, locales, messages, state, themes, or business settings.
12. **Upstream behavior is preserved:** Override native defaults only for reliability, isolation, or compatibility.
13. **Supported versions are considered:** Default behavior works across the declared peer-dependency range.
14. **Defaults are deterministic and isolated:** Avoid ambient state and shared mutable configuration.
15. **Diagnostics remain useful:** Do not suppress upstream warnings without a specific integration reason.
16. **Options factories return fresh values:** Avoid shared mutable options between pipeline executions.
17. **Lifecycle responsibilities remain clear:** `beforeCreate()` does not silently inject defaults; `afterCreate()` is for runtime side effects.
18. **Package exports are standardized:** Keep descriptive names and export `plugin`, `PLUGIN_NAME`, and the type-only `PluginOptions` alias of the public configuration type (not runtime options).
19. **Tests run at the correct level:** Default options and native creation belong in plugin tests; mounted-component behavior belongs in integration tests. Verify that the built package exposes the `PluginOptions` type alias for consumers and generated presets.
